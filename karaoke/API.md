# 视频链接 → 卡拉 OK 成品

本地异步 API，复用当前 F + Anvuew 三轨分离、音频歌词对齐和金色字幕流程。

## 启动

在仓库根目录运行：

```sh
.venv/bin/python -m pip install -r karaoke/requirements-api.txt
.venv/bin/python -m karaoke.api
```

默认监听 `127.0.0.1:8746`。网页点歌台：<http://127.0.0.1:8746/>。交互文档：<http://127.0.0.1:8746/docs>。
API 的依赖文件只安装服务依赖。新检出请按[安装说明](../SETUP.md)准备模型、音频环境和 FFmpeg；模型权重和歌曲数据不在仓库中。

## 网页与共享歌单

网页使用 `GET /v1/room/events` 的 SSE 长连接接收完整状态快照，不轮询。断线后自动重连，重新获取当前状态。下面的 `GET /v1/jobs/{id}` 仍供脚本按需查询。

房间条目的 `lyrics_unavailable` 表示成品没有可显示字幕；`lyrics_need_review` 表示歌词或对齐尚待复核，两者不能混为同一个提示。

| 接口 | 用途 |
|---|---|
| `GET /v1/library` | 列出已知歌曲，实际文件完整时才标记为已准备 |
| `GET /v1/room` | 当前歌曲、播放位置和已点顺序 |
| `POST /v1/room/entries` | 传入 `{ "url": "..." }` 点新歌，或 `{ "job_id": "..." }` 复用已准备歌曲 |
| `POST /v1/room/commands` | `play`、`pause`、`seek`、`next`、`select`、`remove`、`reorder`、`mix`、`ready`、`retry` |
| `GET /v1/room/events` | 推送 `event: room`；空闲时只发连接保活注释 |
| `GET /v1/storage` | 缓存使用量、上限、受保护与可回收容量、准备空间是否足够 |
| `POST /v1/storage` | `{ "limit_gib": 10 }` 修改并持久化上限，返回新的房间快照 |

`pause`、`seek`、`next`、`ready` 必须带 `entry_id`，防止旧播放器事件影响新歌曲。`reorder` 传入完整的 `order` ID 数组，可带 `revision` 拒绝过期操作；当前歌曲保持首位。`mix` 接受 `instrumental`（纯伴奏）、`karaoke`（伴奏＋伴唱）、`original`（三轨一起播放）。

`POST /v1/room/entries` 也接受 `force: true`，与 URL 一起使用时完整重做该视频，用于最终版本的整曲回归；普通点歌和失败重试默认复用缓存。此参数不改变房间队列容量。

`levels` 独立调整三个声部，支持部分更新，例如 `{ "action": "levels", "levels": { "backing_vocals": 0.35, "lead_vocals": 0.2 } }`。键为 `instrumental`、`backing_vocals`、`lead_vocals`，值为 0–1 的有限数。房间快照中的 `levels` 包含全部三个值，手动设置不对应预设时 `mix` 为 `custom`。切歌、暂停、定位不改变音量；选择 `mix` 预设则重置三个值。`storage` 随房间 SSE 快照推送，前端不轮询。

`pitch` 实时设置三轨共同的升降调，例如 `{ "action": "pitch", "pitch_semitones": -2 }`。接受 -6 至 +6 的整数半音数，0 为原调；快照中的 `pitch_semitones` 持久保存，遥控页同步。此命令不改变播放位置、播放速度、音量、预处理结果或缓存音轨。

预处理队列按歌单中尚未开始的歌曲重新排序，不中断当前处理。播放抵达未准备好的歌曲时等待；媒体加载完成后由播放页发送 `ready`，从设定位置起播，不把预处理／加载耗时算入歌曲时间。移除点歌项解除缓存保护；已提交的预处理仍会完成，成品可按 LRU 回收。

浏览器用同一个 Web Audio 时钟播放三条 MP3 试听音轨，MV 静音跟随。普通页面负责播放；`/?remote=1` 只点歌和控制，不发声。完整说明见 [APP.md](APP.md)。

## 提交

```sh
curl -sS http://127.0.0.1:8746/v1/jobs \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://www.youtube.com/watch?v=n5sjpCQhTDk"}'
```

也支持 `youtu.be`、YouTube shorts/live 的录播、Bilibili BV/av 地址、`?p=2` 等分 P，以及 `b23.tv` 短链。一个任务只处理一个视频；直播流、播放列表和超过默认 15 分钟的视频会拒绝处理。

立即返回 HTTP 202：

```json
{
  "id": "任务 UUID",
  "status": "queued",
  "active_stages": [],
  "status_url": "http://127.0.0.1:8746/v1/jobs/任务UUID",
  "cache_hit": false
}
```

### 可选参数

| 字段 | 默认 | 用途 |
|---|---|---|
| `mv_audio` | `instrumental_backing` | 成片使用背景音乐＋伴唱；设为 `instrumental` 只播放背景音乐 |
| `lyrics` | 自动 | 字符串数组或按换行分句的文本；应与该视频版本实际演唱一致 |
| `language` | 自动 | `zh` / `ja` / `en`，也接受 `Chinese` / `Japanese` / `English` |
| `title`、`artist` | 自动 | 覆盖片头歌曲和原唱信息 |
| `force` | `false` | 强制创建新任务，不复用同链接、参数、流水线版本的任务 |

```json
{
  "url": "https://www.bilibili.com/video/BV1bK411W797?p=1",
  "mv_audio": "instrumental",
  "language": "ja"
}
```

## 查询和下载

```sh
curl -sS http://127.0.0.1:8746/v1/jobs/任务UUID
```

状态依次为 `queued`、`running`、`completed`；失败为 `failed`，通过 `error.code` 与 `error.message` 获取原因。`active_stages` 会显示当前正在下载、分离、整理歌词、对齐还是渲染。同一首歌的独立步骤可并行，因此可能同时显示两个阶段。

普通点歌与严格音频验收区分处理。普通点歌先查已发表的歌词文本，核对歌名、歌手与版本，再做声学对齐；该路径的 `validation_scope=playback_lyrics_first`，不声称完成独立 ASR 覆盖率验证。优先使用视频中明确发布的歌词或 LINE MUSIC 歌词，再查询歌词库；歌词库候选另做时长检查。找不到合适的文本时保留无字幕音轨，不回退到 ASR 猜测歌词。文本或对齐失败可返回 `completed` 的可唱版本，`validation_scope=playback_with_lyrics_review`，`quality.playback_fallback` 保留错误与字幕模式，`lyrics_provenance.needs_review=true`。已发表文本的有效逐字时间予以保留；其余只有完整合法唱句时间时显示白字，不制造逐字起点。历史 ASR 草稿仅作诊断，不作为回退字幕。音轨分离、文件和音频重组失败仍然阻止发布。`--audio-only` 固定回归继续执行原有完整验收，任何这类回退都不能计为通过。

多首交错处理时，普通 worker 使用数据目录中的 `stage-locks/` 协调下载、分离、识别／对齐、编码四个独立阶段；同阶段单任务，不同阶段可并行。首次下载和补视频共用下载阶段，避免突发请求和同时改写登录文件。`stage_progress.<阶段>.waiting=true` 表示尚未获得执行机会，等待不计入模型运行超时。任务结束或进程退出会释放阶段锁；共享缓存预算保持不变。

外部语音／歌词服务错误还包含 `error.provider` 和 `error.retryable`：超时、连接或限流可以退避后重试；内容拒绝、认证或权限失败需要人工处理。错误码分别为 `openai_timeout`、`openai_connection`、`openai_rate_limit`、`openai_content_rejected`、`openai_authentication` 和 `openai_permission`。对外只返回固定说明，不暴露原始响应、请求头或密钥；已完成阶段仍按检查点规则保留。

`stage_progress` 按阶段提供实测计数，例如 `{"separate_music":{"completed":12,"total":40,"unit":"chunks","detail":null}}`。下载按视频／音频分别计字节，分离计已处理音频块，对齐计已处理段落／行，渲染计已送入编码器的帧。`total` 缺失时不计算百分比；加载模型、在线歌词请求、封装与校验仅提供阶段或 `detail`。这些是当前步骤的工作量，不能相加当作整首歌的时间百分比。只有成品通过校验后才会进入 `completed`。

语音识别出现局部长串重复循环时，先用前后有辨识度的歌词包住异常段，最多重识别 90 秒音频。新结果必须在原位置匹配两端歌词（文本相似度至少 80%、起止相差不超过 2 秒），只替换两个边界之间的文字与实测词时间；拼接结果仍须通过完整异常检查。局部恢复不可用时，依次用已有本地模型检查同一录音的原始混音和主唱轨，保留语言、录音时长、时间顺序与异常文本校验；恢复依据及拒绝原因写入 `asr/original-recovery.json`、`asr/lead-recovery.json`。主唱分离在识别前完成，封装与重采样仍可和分离并行；主唱输入变化会使相关识别缓存失效。仅这些本地候选仍不可用时，再用 `gpt-4o-transcribe` 在整首上下文中恢复歌词文本（可用 `KARAOKE_ASR_FALLBACK_MODEL` 配置），同时把 Whisper 的粗定位改为 30 秒片段、最多 3 路并发；仍循环的片段不提供词时间。恢复文本不带词时间，`recording_bounds` 只是录音范围，后续仍由声学强制对齐生成起唱时间。恢复过程记录在 `asr/run.json`，局部候选保存在 `asr/loop-repair.json`，持续异常会明确失败。这些边界检查不代表逐字起音准确率。

每次转录 API 的原始回包独立缓存在任务目录 `asr-requests/`，包括未通过校验的回包；按音频哈希、请求参数、请求实现及回包哈希校验后复用。后续文字处理失败不会重新请求相同音频，修改局部拼接算法也不丢弃已有回包。它们和其他阶段产物一起计入缓存预算，可由正常 LRU 回收；歌词、粗定位和日志也保留供复现。

歌曲信息提取的成功结果另存为 `song-metadata.json`，按输入视频信息、模型、实现和结果哈希检查复用。重做转录或修改对齐代码不会重新选择歌手名称或简介中的歌词行；新的转录仍正常参与歌词校验。输入、模型或结果文件改变时才重新提取，保留视频信息中提供的原文歌手名，避免仅用转写名称检索到不同歌词来源。

日文粗定位先按原文匹配。汉字与假名写法不同而未定位的连续句段，再用现有日文发音字典匹配；只使用前后已定位句之间的 ASR 词，不移动已有句子，也不改变歌词或生成时间。恢复的锚点标记 `match_basis: pronunciation_recovery`。缺词及遗漏唱段仍须通过原有整曲检查；读音匹配本身不代表逐字起音准确率。

只有标点的转录也会触发恢复；跨多段重复同一句且过半片段时间塌缩的结果视为解码异常。局部连续片段均不超过 25 ms、间隔不超过 25 ms、相同内容至少重复 8 次，也触发恢复，避免正常段落掩盖局部解码循环；正常计时的副歌和间隔开的短音节不受这条规则影响。自动语言请求在恢复时重新识别语言，不固定使用异常转录的语言标签；按可用分段词数中的字符量汇总语言证据，写入 `recovery.language_evidence`。用户显式指定的语言仍然保留。这些仅是恢复触发条件，不等于歌词准确率。

句子或词时间戳倒序、负数、非有限数或起止颠倒也会触发恢复，避免错误粗定位把多句歌词挤进很短的音频窗口。分段重试仍有这些问题时，舍弃该段的词时间并保留诊断；不排序、平移或钳制时间戳来伪造可用结果。

同一时刻堆积至少 8 个含文字的零时长词单元，也会触发重识别。少量零时长子词仍交给后续声学对齐；该阈值只用于决定是否重识别，不表示这些词一定没唱，也不据此删词或放宽最终校验。

流畅的短句也可能是前奏／尾奏上的幻听。若 ASR 的无语音概率至少 0.6，且该段至少三个词单元中有一半时间塌缩，或整段被压到 0.2 秒以内，也进入独立重识别。无语音概率本身不触发删词；有正常词时间的轻声演唱仍保留。这是复核触发条件，不是歌词正确性的证明。

自动语言识别返回中文、日文、英文以外的结果或缺失语言时，也先进入同一套有上限的恢复流程，避免错误语言标签直接结束任务。恢复片段仍识别为不支持的语言时不采用其词时间；没有足够的受支持语言证据仍然失败，不根据歌名强行指定语言。

恢复过程中，30 秒窗口仍无法提供有效词时间时，仅将该窗口分成最多两个不超过 15 秒的片段再试一次；不足 30 秒的尾窗均衡拆分，正常窗口不重跑。完整歌词继续使用整曲识别文本，短片段只补充真实识别得到的词时间，不拼接片段文本。仍异常的片段保留诊断、舍弃词时间，歌词匹配及最终对齐门槛不变。

本地恢复使用自动语言时，超过 30 秒的录音在四分之一、二分之一和四分之三处分别检查一个最长 30 秒的窗口，按多数一致的语种识别整曲，避免仅凭前奏判定语言。短录音使用完整片段，显式指定的语言保持不变。窗口分歧时缓存诊断并拒绝该本地候选，继续原有后备路径；不会退回前奏的猜测。窗口与语言概率保留在 `language_detection` 中，它们不是字幕起音准确率。

整曲恢复文本的文字单元不足分段词结果的一半时，不能直接当作完整歌词。若初始整曲文本没有循环，且与分段词结果双向匹配均至少 55%，则复用初始文本，继续使用有效的分段词时间；不恢复初始异常时间戳，也不补写歌词。否则失败并保留词结果。选择依据写入 `asr/text-selection.json` 和 `recovery.text_selection`；这些是截断检测及文本选择依据，不是逐字起音准确率。

复用初始文本时，若文字与原始段落完全一致，保留原始文字分段供数字静音过滤使用，避免整曲合并后掩盖尾奏中的幻听；粗定位仍使用恢复后的词时间。若视频简介候选在复核后仍不匹配音频，仅在整曲 ASR 文本与独立分段识别双向匹配均达到 55% 时，才改用这份 ASR 草稿。拒绝的简介、匹配率及来源保存在歌词 provenance 中；用户提供或已核对的歌词不走此回退，后续字幕校验仍全部执行。

歌词与 ASR 词序列的粗匹配先最小化文字编辑距离，再在同分结果中选择歌词内部跳过片段更少的匹配；开头和结尾的非歌词片段不计入内部跳段，避免把对白里零散的字母拼成一句歌词。时间仍直接来自被匹配的 ASR 词，整体及逐句匹配门槛不变；匹配率不代表起音准确率。该步骤使用固定版本的 Biopython 全局序列对齐器。

歌词来自用户、已核对目录或视频简介时，重识别前后的粗定位都可作为候选。原始候选必须语言匹配、词时间有效且顺序正常；选择整套文本匹配更好的候选，不拼造时间、不改歌词。选用来源和两套覆盖率记录在 `asr/filtered.json`，后续声学对齐和最终质量门槛不变。纯 ASR 草稿不靠原始转录自我验证。

上述歌词的粗匹配仍不足时，最多补识别三次：从未匹配段前后的有效锚点选取上下文，每段不超过 45 秒。上下文过长时缩至最近的相邻句，仍过长则检查边缘窗口；人声窗口不能改善匹配时，可检查同一时间范围的原始混音。经过独立分段重识别的 ASR 草稿也可走此流程。ASR 只接收音频和已确认的语言，不接收目标歌词；只拒绝局部异常的词时间，剩余结果仍须通过完整异常检查。仅采用提升整体匹配、时间顺序有效的词结果，保留窗口外侧的原词时间和全部歌词文本。每个窗口及音频来源有独立的输入、代码和结果检查点；诊断保存在 `asr/anchor-recovery.json`。补识别后仍使用原来的匹配门槛，失败则停止。

分块对齐遇到跨窗口冲突时，检查已有上下文预测，优先采用同一窗口覆盖相邻两句的结果，也允许采用其他重叠窗口里的完整单句。只有冲突减少且没有新增词起点、句尾顺序或过度重叠问题时才采用。这里复用后续字幕行校验，不通过移动时间戳修补；找不到合法候选时保留失败。

若对齐器返回的词与输入歌词不一致，对同一音频窗口只重试一次：关闭句间停顿填充并动态选择注意力头。候选须逐句完整覆盖原歌词，全部词都有有限、正时长、顺序正确的声学时间，且通过原有行时间校验才可采用；不删除重复词、不补时间。两次结果保存在 `alignment/raw.json` 的 `text_recovery` 中。原始结果在拼接校验前落盘，失败后也能复现；此检查不代表人工起音准确率。

整行仍没有时间时，再用相邻一句有粗定位的歌词扩充上下文，进行一次不限制单词时长的声学重试。它针对长哼唱被语音模型的时长限制截断、或孤立粗定位选错演唱位置的情况；只有全部文字和词时间通过原有完整性、顺序及范围检查才采用，原结果和候选保存在 `unresolved_recovery`。英文音素输入保留连字符，避免连续元音被误读成带额外辅音的单词；纯 `Mmm` 哼唱使用持续的 /m/，不按多个字母名称发音。

连续重复唱句只有最后一遍没有时间时，检查已定位唱句之间最大的空档。分别对空档及前后唱句的上下文做声学复核，窗口不超过 45 秒；候选的全部词必须落在空档内，至少一半且不少于两个相邻词的起点须在两次预测中相差不超过 200 ms，贴住裁剪边缘的词不作佐证。通过才将真实预测插回原顺序，保留全部歌词，其余词时间不动；原始预测和复核结果保存在 `alignment/raw.json` 的 `repeat_recoveries` 中。仍须通过后续音素对齐和全部输出校验；窗口一致性不代表人工起音准确率。

映射显示文字时保留词间标点，包括模型拆开的英文缩写中的撇号；显示范围调整不改变音频测得的词起点，缺失的正文仍会被完整性检查拒绝。

分行产生的独立引号、句号等纯标点行并回相邻歌词，保留所有非空白字符及原顺序；开头标点随第一句显示。自动转录、视频简介和用户歌词采用相同处理，纯标点输入仍拒绝。对齐拼接也拒绝没有可唱文字的独立行，避免跳行后把下一句错误配给两个行号。英文音素对齐使用与词起点评测相同的词筛选方式，独立省略号等不作为发音词元；这些标点留在相邻词的显示范围内，不新增或改动起音时间。

英文默认保留整曲声学对齐，但用已通过顺序校验的 Whisper 唱句建立上下文范围。词时间跑到所属上下文之外时，仅对受影响的整块重新做声学对齐；重试在原窗口前后各多包含一句，避免粗定位裁断长音或混淆相似的哼唱。保留原词序和其他块的结果，不把词时间直接改成范围边界或粗定位时间。原范围、实际重试范围、预测及采用情况写入 `english-onsets/run.json` 的 `context_retries`。重算仍越界或出现顺序冲突则失败；最终音频验收也检查完整的 `english_context_scope`，不能仅凭文件、哈希和时间单调计为通过。这是跨段错误保护，不是人工起音准确率。

重复唱句的音频匹配若因时长差异或无效特征找不到合法路径，只拒绝该候选并记录原因，继续检查其他参考句；没有可用候选时保留此前的时间，仍须通过后续字幕校验，不放宽匹配路径或最终门槛。

合并的中文字组若仍无法拆开，会检查相邻歌词的中文上下文，裁掉英文等非中文唱词及对应音频，防止中文音素被强行对齐到英文。旧的相邻字边界挡住候选起点时，可以将这些相邻字一并重新对齐，但每个改动的字都必须通过同样的三个声学窗口及原音／人声双视图复核，不能直接挪开旧边界。窗口超过 30 秒、裁剪后不足三个不同窗口或无法获得独立证据时保留失败。

同曲重复唱句也可提供拆字依据：仅使用已通过跨模型复核的参考字；分别计算原音和人声的音高、频谱四条匹配路径，沿用已有重复唱句的路径代价和一致性检查。映射出的目标起点还必须得到目标原音和人声的独立声学复核，并有可听音频及合法的相邻字范围；不直接复制副歌间的固定偏移。过程及拒绝原因写入 `context/song/verified-repairs.json`，参考字和映射字都不构成独立人工准确率证明。

残余字组可再用可选 Qwen3 ForcedAligner 的原音／人声双视图复核；仍要求 SOFA 三个上下文的起点稳定、两份独立预测均在 100 ms 内、正时长、可听声音及合法顺序。Qwen 只提供独立证据，不直接替换主对齐时间；SDK 的插值及时间修补关闭，原始异常时间会被拒绝。依赖在子进程隔离，诊断见 `qwen-witnesses.json` 与 `qwen.log`，模型和配置变化只使相关对齐缓存失效。这个后备检查仍不能代替人工起音标注，校准范围见[自动检查说明](docs/automatic-quality.md)。

中日文歌曲里的英文段若仍有多个词合并高亮或单词被拆断，会用现有英文 SOFA 模型在三个上下文重新对齐，并用 MMS 分别核对原音与分离人声。单词跨越多个字幕单元时，先扩展到完整单词覆盖的单元，再用新的声学预测取起点；范围若涉及未分开的中日文字或已核验的重复片段，保留原结果。混合语言句只截取已有字词边界限定的连续英文段，两种模型和两份音频都受相邻外文的时间边界约束；无法取得三个不同窗口时保留失败。沿用 80 ms 的上下文极差、100 ms 的独立模型差异及原有音量、邻词范围和顺序检查；不满足就保留原结果及失败。只替换证据完整的缺失高亮范围，其余词和相邻中日文保持不变，诊断见 `context/song/latin-repairs.json`。这仍是自动候选校验，不代表人工起音准确率。

固定样本回归控制器 `karaoke.tools.soak` 会把各阶段日志末尾最多 16 KiB、轻量对齐诊断及 ASR 原始响应压缩保存到 `service-data/soak-100/`，其中每份 JSON 最多 2 MiB。被拒绝的恢复响应、最终字幕和产物清单也会保留；最终字幕的覆盖检查结果及其输入哈希写入 `lyric-coverage-validation.json`，一同归档，便于在任务缓存被 LRU 回收后复查拒绝原因。归档按诊断内容的 SHA-256 区分，同一任务再次报相同错误时也不会覆盖早先的证据；记录不包含音视频，也不代表该样本已通过。

控制器将 DNS 解析失败归为网络故障并退避，不等待代码版本变化才允许重试。同一平台的新退避只延长已有等待，不会让后来的短等待覆盖先前的长等待。服务主动关闭或 macOS 明确报告正在关机时，保留原始错误和阶段检查点，短暂等待后允许同版本重试；这类本机中断不触发视频站点或 OpenAI 的全局退避。普通模块加载错误仍按软件故障处理。

失败任务中已经验证完整的视频下载也暂存于同一缓存预算内。重试相同 URL 时先核对文件 SHA-256，再复用本地视频，避免重复下载触发站点限制；这些原视频同样优先参与 LRU 回收。`force: true` 不复用失败任务的下载。

失败后的普通重试也复用逐阶段检查点：解码、两次分离、双轨／三轨封装、ASR、歌词整理、各步对齐和渲染分别保存输入、配置、相关代码与产物指纹。同一请求可在原任务 ID 上重新排队，`attempt_count` 增加；校验通过的阶段跳过，失败或已损坏的阶段重跑。改变对齐代码不会使音乐分离失效；下游通过实际输入内容决定是否失效。成功只在输出完整并通过校验后记录，半成品不会作为检查点。结果的 `reused_stages` 列出复用步骤。

对齐阶段只跟踪自己使用的模型：粗对齐跟踪 Whisper，音素、重复句和上下文对齐跟踪当前语言的 SOFA。新增未启用的实验模型不会使生产版本或已有对齐缓存失效；更新其他语言的生产模型会更新整体版本，但不会重算当前语言的无关阶段。

检查点和中间音频与成品使用同一缓存预算；失败时保留已完成阶段及 JSON 诊断，成功后只保留最终产物。LRU 仍可回收未受保护的失败任务，所以断点恢复以文件尚未被回收为前提；不会为了保留检查点提高 10 GiB 上限。`force: true` 始终重新完整处理。

房间快照也包含每首运行任务的 `stage_progress`，通过 SSE 更新。进度来自子进程的结构化标准输出；计数更新通常限频为每 0.5 秒一次，阶段切换立即推送。前端不轮询，不根据经过的时间伪造进度。

曲库从入队开始就包含歌曲，状态可以是 `queued`、`running`、`completed`、`failed`、`video_evicted` 或 `evicted`；静态目录中尚未提交的歌曲为 `unprepared`。同一视频只展示最近一次任务。`job_id` 也可指向尚未完成的任务，再次点播时复用该任务，不重复下载或处理；只有 `status == "completed"` 才表示已准备好。房间 SSE 快照的 `library` 与 `GET /v1/library` 使用同一份数据，元数据、语言分类和进度一并推送。

页面语言分类优先采用用户指定值，再使用已生成结果、当前音频语言信息或已知曲目目录。处理初期可用所选音频轨的语言标签暂时分类，ASR 返回后立即更新，歌词整理后再次确认。未知语言暂时只列在「全部」，不会按标题文字或字幕语言猜测演唱语言。

取得下载元数据后，`song_info` 立即提供 `title`、`artist`、`duration_seconds`，并通过房间 SSE 更新歌单，不必等整首准备完成。优先使用视频的音乐标签，否则先显示视频标题；不把上传者当成原唱。歌词整理完成后再更新歌曲信息，用户填写的歌名／歌手始终优先。`input` 保持原请求，`result` 仍只在成品完成后提供。

LRU 优先回收视频：任务为 `video_evicted`、`restore_video: true`，仅 MV 接口返回 HTTP 410，其余音轨、字幕和封面仍可获取。提交相同输入（`force: false`）或用原 `job_id` 点歌，会复用原任务进入 `queued` / `running`，只下载、核对源音频指纹、重新合成视频；不会重跑模型。恢复沿用原先算好的结果，即使渲染器版本更新；成功后清除 `restore_video`，恢复耗时单列在 `result.video_restore`。恢复失败保留产物，房间的 `retry` 仍只补视频。源音频指纹不同报 `verify_video_failed`，可用 `force: true` 显式完整重做。

视频回收后仍空间不足，才完整回收任务为 `evicted`，全部原文件接口返回 HTTP 410。重新提交同链接或用原 `job_id` 点歌会完整准备。缓存不足导致准备中断时错误码为 `cache_full`；不会删除待唱歌曲来掩盖空间不足。默认上限、统计范围和运行中写入限制见 [缓存说明](APP.md#本地缓存上限)。

完成后的 `result.artifacts` 每项包含 `url`、`bytes`、`sha256`：

| 名称 | 文件 |
|---|---|
| `mv` | 已烧录字幕的完整 MP4；混音含义见 `result.mv_audio` |
| `instrumental` | 背景音乐 WAV |
| `backing_vocals` | 伴唱 WAV |
| `lead_vocals` | 主唱 WAV |
| `instrumental_preview` | 背景音乐 MP3 |
| `backing_vocals_preview` | 伴唱 MP3 |
| `lead_vocals_preview` | 主唱 MP3 |
| `subtitles` | 包含逐字／词时间的 JSON |
| `poster` | 可选的本地 JPEG 封面：优先视频缩略图，获取失败时截取 MV 画面 |

文件接口支持 HTTP Range，可直接交给播放器或下载。处理完成前访问文件返回 409；未发布的内部文件无法通过文件接口读取。

```python
import time
import httpx

base = 'http://127.0.0.1:8746'
with httpx.Client(timeout=30) as client:
    response = client.post(base + '/v1/jobs', json={'url': 'https://www.youtube.com/watch?v=n5sjpCQhTDk'})
    response.raise_for_status()
    job = response.json()
    while job['status'] in ('queued', 'running'):
        time.sleep(2)
        response = client.get(job['status_url'])
        response.raise_for_status()
        job = response.json()
    if job['status'] != 'completed':
        raise RuntimeError(job['error'])
    for name, artifact in job['result']['artifacts'].items():
        print(name, artifact['url'])
```

`GET /v1/jobs?limit=20` 列出近期任务；`GET /health` 返回队列和正在处理的任务。

## 自动歌词与质量边界

已核对的本地歌词只在视频身份和时长匹配时复用。新视频从分离人声生成 ASR，按原文顺序分行，仅改变空白，不让文本模型增删歌词、重复句或改写唱词。结果标为 `asr_draft` / `needs_review`，附转录指纹；识别本身的错字、对白或幻听仍可能需要复核，这不是出版歌词的正确性保证。文本和词时间支持不足、粗时间轴冲突或字体缺字时仍明确失败，可提供修正后的 `lyrics` 再提交。文字来自 ASR 时，文字匹配率主要用于一致性检查，不能当作独立的识别或起音准确率。

分离人声的转录异常且局部恢复未解决时，先用已安装的 `large-v3-turbo` 识别同一录音的原混音，再考虑整曲在线重试。两份音频的时长必须一致；自动语言请求重新检测语言，显式指定的语言必须匹配。仍有重复、塌缩时间、越界或缺失词时间的候选不会采用。原始响应按音频、模型和代码缓存，选择理由保存在 `asr/original-recovery.json`，原混音也参与阶段缓存签名；此步骤只恢复 ASR 草稿，后续歌词和逐字对齐检查保持不变。

局部重识别覆盖重复循环，以及同时出现无声警告和词时间塌缩、整句词时间重合的异常片段。中间异常若带有解码窗口 `seek`，同一窗口内的其他句子也不能作为可靠拼接边界，改从窗口外选择锚点；缺少窗口信息时保留原有选择方式。中间片段仍须匹配前后唱句，保留片段外的原词时间，并对拼接后的完整转录重新执行质量检查；没有可靠前后边界或超过 90 秒就不拼接。诊断保留触发片段索引及窗口标识，不按文字内容删除疑似幻听。

转录语言采用用户显式指定值；未指定时从音频自动检测。下载器提供的音轨语言标签可能不准确，只用于页面暂时分类，不限制识别语种。标题文字和字幕语种同样不作为转录语言。

两份整曲转录都无法提供完整歌词时，保留独立分段识别的词时间，将转录正文留空，再检查用户歌词、已核对目录或视频简介中的原文。只有独立歌词通过原来的音频匹配和后续对齐检查才能继续；没有独立歌词或内容不匹配仍会失败。被拒绝的转录保留在诊断文件中，不用它补字、拼接歌词或生成时间。

文本模型整理标题、音乐标签和上传者字段；视频简介含完整歌词时，它只返回所选原文的行号，代码检查范围、顺序和重复行号后提取原文，不让模型生成或改写歌词。保留原文分句，不按固定字数另拆对齐行，以免将日文词尾或英文末词孤立成行；独立标点仍并入相邻句，原有单行长度限制仍生效。保留简介指纹和行号，来源标为 `video_description`；这些歌词仍经过同一套音频匹配与对齐门槛。简介没有完整歌词或行号无效时使用 ASR 草稿。歌曲信息请求失败时保留视频标签和标题，并将原因记录在 `lyrics_provenance.metadata_error`；不会反复提交被拒绝的内容。ASR 阶段的错误仍正常报错和退避。

同一 YouTube 视频若提供与演唱语言一致的人工字幕轨，可用其文本替代 ASR 草稿。排除自动字幕、自动翻译和其他视频的轨道；文本与音频转录的双向支持均达到 55% 才采用，来源记为 `source_manual_subtitles`。保留原文和重复句，字幕的显示时间仅用于检查文件范围，不作为逐字起音时间；后续声学对齐及质量检查不变。原始响应单独缓存为 `source-captions.json`，临时错误按服务端提示或至少五分钟退避；取不到字幕时保留 ASR 路径。404、429 等字幕请求错误保存在诊断的 `error` 字段，不中断后续歌词查找和原有质量检查；缓存命中时也保留错误和退避时间。

仍只有 ASR 草稿时，可从 [LRCLIB](https://lrclib.net/docs) 检索独立歌词文本。先要求歌名、歌手相符（允许繁简体及中英双语名称中的中文别名），版本标签不作为别名删除；录音时长误差不得超过 2%，容差下限 3 秒、上限 10 秒。然后沿用双向 55% 音频文字支持门槛，保留原文和重复句，来源记为 `online_lyric_text`。只使用纯文本，完全不采用歌词站的时间戳；逐字时间仍由本视频的音频对齐、复核，所有后续检查不变。响应及错误缓存在 `lyric-lookup.json`，临时错误遵循至少五分钟及服务端 `Retry-After`；查不到、版本不符或网络不可用时保留 ASR 路径。此项是新歌的在线检索，不依赖被 `KARAOKE_DISABLE_LYRIC_CATALOG=1` 禁用的开发歌曲本地歌词库。它不替换用户提供、已核对或来自视频本身的歌词，也不代表文字或起音已经达到人工标注准确率。

视频容器若在原音频首尾填充了全零静音，整体时长匹配失败后会按原始 PCM 的非零内容时长再用同一容差比较。只有所有声道都严格为零的首尾可排除，微弱声音仍计入；全静音、非有限采样或与源时长不符的文件不提供此依据。音频文件、帧数和字幕时间轴保留不变，匹配依据及源文件哈希记在 `lyric_lookup.duration_basis`。

歌名末尾括号中的明确影视用途说明（例如 `电影《片名》主题曲`）可以作为歌名别名处理。只识别这类完整说明，不泛化删除括号；现场版、混音版、语言版本及其他限定继续参与匹配，歌手、时长和音频文字支持检查不变。回放失败样本时须保留正式流程实际产出的短歌名和歌手，不能预先改成歌词库的标题再宣称验证通过。

原视频标题明确写有 `Live from/at/in 场地` 时，歌词候选的曲名或专辑必须标明同一场地；不会因文本模型缩短了歌名就丢掉这项约束。其他现场或没有场次信息的歌词不采用，继续检查本录音的 ASR 草稿；仍保留完整性和对齐门槛。这项保守校验不把相似时长当作同一演出，也不把未标注的现场自动视为录音室版本。

简介省略重复副歌时，用已有 ASR 检查唱句间未覆盖的音频：至少 24 个文本单元、连续两行原歌词与转录相似度达到 90%，首尾均有粗定位支持，才可复制该原文段落。多解、原唱句被移到另一遍、插入句超出空档均拒绝；用户歌词和已核对目录不自动增补。原文、词时间和复制范围保存在 `asr/lyric-repeats.json`，不新增下载或 ASR 请求。增补后仍做正常声学对齐；最终流程及音频验收再次检查是否遗漏已识别的重复段。这只能发现有转录证据的漏段，不代表歌词完全正确或逐字起音精度达标。

另外反向检查整首识别结果是否被歌词覆盖，防止简介只引用结尾几句却因匹配率高而通过。先完成有证据的副歌增补，再检查至少 55% 的识别单元能按序匹配，且字幕前、后、句间没有整段未覆盖的识别内容（沿用至少 24 单元的唱段门槛）。检查使用完整恢复词流，不因选择了另一套粗定位而丢掉已识别的唱段。简介摘录仅在完整 ASR 文本获得独立词流支持时回退；用户歌词不改写。诊断保存在 `lyric-repeats.json` 的 `lyric_coverage`，最终产物验收会重新计算，不相信先前的通过标志。这是漏段检查，短即兴词、未识别出的歌词和毫秒起音精度仍不由它证明。

### 先验证音频

定位失败歌曲时，可在同一个任务目录运行 `python -m karaoke.pipeline --request REQUEST.json --output JOB_DIR --audio-only`。该模式只请求音频流，执行同一套解码、两次分离、精确封装、转录、歌词及逐字对齐，输出 `audio-result.json` 和七项音频／字幕产物，不生成 `result.json` 或 MV，也不能计为整曲 MV 回归通过。用 `karaoke.tools.soak.verify_outputs(..., audio_only=True)` 校验母版重组、文件哈希、全部 MP3 解码和字幕完整性。

共享服务上的测试用 `python -m karaoke.tools.soak probe --manifest MANIFEST.json --data-dir DATA_DIR --job-id JOB_ID`。先暂停批量控制器及预处理 worker，并通过普通点歌接口注册任务；该命令检查来源退避和 worker 暂停状态，使用服务的缓存回收接口监测共享预算，超限时终止本次测试并保留检查点。它不会启动其他样本或将音频通过记作 MV 通过。

交互式修复可以向 `run_probe` 传入自己创建的暂停文件原文 `resume_preparation`：在暂停期间认领已注册任务，然后恢复普通调度，与新点歌曲共用阶段锁和缓存预算。进度仍由子进程标准输出推送；修复控制器负责验证成品后发布结果。外部控制器写入本地任务库后可调用 `POST /v1/room/events` 通知 SSE 更新，该接口不接受或修改任务结果。严格音频验收默认继续独占，不能使用此选项改变验收口径。

重试按失败原因计时：OpenAI 暂时性错误从 30 秒起退避，保留 `Retry-After` 或响应中的重试时间，不能早于服务端要求；请求过大、额度不足和鉴权问题等待配置修复。限流按模型隔离，可选元数据模型的额度不阻塞 ASR。视频 DNS／超时从 60 秒起、单个资源的 403 从 5 分钟起退避，均不冻结整个视频来源；429 才记录来源限流，登录验证和不可访问的视频停止自动重试。已有明确限流期限不会因另一次失败而缩短。

同一次下载先报 429、随后要求登录时，两种限制同时保留：该歌曲继续等待登录问题解决，同一来源的其他下载也须遵守 429 退避；不会因最后一条登录提示而漏掉前面的限流。

单首 `probe` 同时检查整曲任务记录、音频任务记录和来源退避，以最晚的截止时间为准。音频刚失败时，即使整曲记录没有等待期限，也不会立即再次下载或调用模型；退避拦截不改动已有阶段产物。

歌词粗定位缺失时，局部补识别也覆盖整首开头和结尾：缺口由已有唱句与录音首尾限定，再截取不超过 45 秒的片段。录音边界不作为歌词起止时间；候选必须提供有效的实际词时间并改善原有文字支持。整首没有任何可用锚点时仍失败，不猜测唱句位置。

固定样本音频回归使用 `python -m karaoke.tools.soak audio-run --manifest MANIFEST.json --data-dir DATA_DIR`。逐首验证七项音频／字幕产物，遇到软件失败立即停下供修复；结果单独写入 `audio_attempts`，仅统计同一实际 pipeline 版本。`audio.pause` 可在当前首完成后暂停。通过的任务记为 `audio_ready`，移除本控制器加入的待唱条目，释放缓存保护；它没有完整 MV，因此网页仍显示未准备，后续点播从保留的检查点继续。旧 worker 队列中的此类条目不会擅自重跑。

先处理已有音频失败和其他已到重试时间的历史失败，再处理未完成样本；旧版本已通过样本的复验排在最后，避免延迟修复效果的验证。外部失败在到期后按最久未尝试的顺序重试，避免刚超时的请求连续抢占其他失败样本。尚处于退避期的外部失败不阻挡其他可运行样本。

需要只复测固定清单内的一首时，在 `audio-run` 后加 `--case-url VIDEO_URL`。它保留批量暂停文件，仅注册、处理和验证指定来源，使用同一个缓存预算与结果账本，完成后退出；已有运行任务、同版本未修复失败或来源退避仍会阻止重复运行。这样不必先恢复整批队列再抢时机暂停。

明确决定暂缓某个难例、先检查其余样本时，可用 `audio-run --defer-url VIDEO_URL`，支持重复指定。暂缓来源仍保留在固定清单及失败记录中，不计通过；其余样本仍在新的软件失败处停下。暂缓列表写入 `audio_deferred_urls`，全部通过的分母始终是原完整清单。该模式仍遵守 `audio.pause`。

需要先摸清整批失败范围时，加 `--keep-going`：单首处理或产物校验失败后保留失败状态与诊断，继续其他样本。同版本软件失败不会再次提交；同版本外部错误的重试排在其余可运行样本之后，仍遵守原退避时间和次数限制，旧版本历史失败继续优先排查。空间不足、worker 恢复工作或运行环境变化时停止。只移除控制器自己加入且非当前播放的条目，释放缓存保护；失败检查点仍参与共享 LRU。`audio_keep_going` 记录此模式，失败与暂缓样本始终留在分母中。

音频通过后，在同一目录取消 `--audio-only` 再运行：仅补同一来源的画面，将已测试的音频流原样封装到独立容器，并检查 PCM 指纹。原音频文件和阶段输入不变，补画面不会使分离和对齐缓存失效；补视频失败也保留原音频和检查点。全部文件及播放验证通过后才计入最终 100 首结果。

逐句音素细化有时会让后一句提前越过前一句。接口会检查全局起点顺序，对冲突行回退到原有粗对齐，并通过 `quality.line_order_fallback_lines` 标记；不会手工平移某个字来凑顺序。粗对齐本身有冲突时不生成伪造的时间轴。

粗对齐修复会同步保存所选窗口的原始词结果，选择记录位于 `alignment/run.json` 的 `boundary_reconciliations`；没有可用预测仍然失败，不通过平移、插值或放宽门槛过关。这项检查保证拼接一致，不代表人工起音准确率。

中文和日文沿用歌声音素与三窗口筛选；英文沿用歌声音素起点和 Whisper 近邻融合。所有语言都使用当前句＋下一句、琥珀色点亮、硬切、片头信息和四秒开唱提示。视频中的旧字幕不参与歌词识别或对齐。

母版是未缩放的 float64 WAV，按 `(主唱 + 伴唱) + 背景音乐` 合并验证原始 PCM。MP3 和 MV 使用同一个防削波增益。编码试听允许一个 MP3 帧以内的末尾静音填充；缺失音频或新增非静音样本仍失败。精确还原不等于分离纯度，也不证明亮字准确率；结果中这两项没有伪造分数。

MP3 试听使用 LAME 命令行写入完整的尾部填充信息，避免某些末帧长度解码后多出采样。公共增益先应用于临时 24-bit 整数 PCM WAV，避免链接 libsndfile 的 Linux LAME 自动归一化浮点输入；编码完成即删除，原 float64 母版不变。仍按原始采样率、声道、帧数、峰值和尾部静音验证，不通过裁掉验证结果或放宽阈值处理异常。

若有损编码使任一试听轨的解码峰值达到 1，则按实测峰值降低整组公共增益，重新编码所有试听轨；三轨模式也包含 KTV 混音，MV 使用最后验证通过的同一增益。最多编码三轮，仍削波就失败；长度、格式或非静音尾部错误不会触发降增益重试。母版不改动，各轨不单独归一化。

## 配置

### 本机下载、GPU 机器处理

`python -m karaoke.tools.soak audio-fetch --manifest 固定清单 --data-dir 数据目录 --keep-going`
只下载音频并核对来源、哈希和全长解码，沿用普通点歌注册、单实例锁及共享缓存监控。
它将结果写入 `download_attempts`，不会写成 `passed_audio` 或完整 MV 通过；任务记为 `source_ready`，
页面显示尚未准备好，移除控制器自己的点歌项后可正常参与 LRU。再次提交复用来源文件，接着计算。
支持同样的 `--case-url`、`--defer-url`，批量暂停文件为清单旁的 `download.pause`。
登录验证或来源退避必须先解决；遇登录阻塞立即停止后续下载。

迁移时在目标服务正常注册同一来源，再复制该任务的 `source.json`、`download/source.mkv`
和 `download/source.info.json` 到目标任务目录。传输前后核对来源与哈希，保留固定清单和失败历史。
目标服务设置 `KARAOKE_REQUIRE_CACHED_SOURCE=1` 后运行原有 `audio-run`；缓存缺失或损坏立即失败，
不会重新访问媒体下载站点。远程仍需 ASR／文本服务访问和相同模型，音频产物继续逐首完整验证。
离线模式的 LRU 会保留已登记的源音频（包括同时带视频的源容器）、来源信息和轻量诊断，空间不足时先回收计算产物，
任务回到 `source_ready`，后续仍逐阶段核对缓存。源文件也计入同一缓存上限；若仅源文件和
受保护任务就已占满，停止准备，不删除源音频或扩大上限。导入、导出进程须继承相同的离线配置。

`KARAOKE_SEPARATION_BATCH_SIZE` 控制 RoFormer 每次前向计算的音频窗口数，默认 1。
大于 1 时使用批量窗口调用，保持原窗口长度、重叠、尾窗、float32 精度和相加顺序；
没有打开自动混合精度。该设置参与流水线版本及阶段检查点。不同硬件或 batch 的通过数不能合并。
`benchmark_neural.py --inputs` 也支持多条输入共用一次模型加载。ASR 和对齐仍走各自流程，
不能把分离的 batch 设置称为整条流水线批处理；吞吐提升须在目标 GPU 上实测。

### 本地 Whisper 批处理

`KARAOKE_ASR_BACKEND=local` 使用本地 faster-whisper / CTranslate2 的 Whisper large-v3，
模型目录由 `KARAOKE_WHISPER_MODEL` 指定，必须已经下载完整；推理不自动下载模型。
`KARAOKE_WHISPER_BATCH_SIZE` 控制同首歌曲最多并行解码多少个 30 秒窗口（默认 8，范围 1–32）。
包括最后不足 30 秒的片段，覆盖整首音频；不使用可能删掉弱歌声的语音活动过滤。
采用 float32 计算、beam size 5 和固定 temperature 0。自动语言识别从录音中部三个窗口投票。
批次大小、推理库版本和模型文件版本均参与流水线与检查点指纹。

本地模式不请求远程转录、文本整理或音频分类接口，也不在线查找歌词／字幕。
无声警告的异常检测包含正好挤在片段结束点的零时长词，避免这些词漏过恢复检查；不把下一句的正常词算入前句。
若整句及其前后 250 ms 的有效音频均为数字零，句内完全匹配的词即使挤到文件结束之外，也可随这句一起剔除，并记录其静音父句。没有明确父句、归属冲突、负时间或附近仍有微弱声音时，继续保留异常并走恢复流程，不按音量阈值删词。
保留用户提供的歌词和已下载的同源字幕；否则从本地转录逐字保留文本，仍需通过原有完整性和声学对齐校验。
ASR 固定宽度断行若留下孤立的单字或单词，会在同一短句内平衡末尾两行；不拆开外文单词、不删改文字、不跨原始短句合并，也不调整时间。最终起点仍由声学对齐产生并单独校验。
异常转录可用已有本地 large-v3-turbo 检查同源原音与主唱；恢复失败保留诊断并明确失败。
重复短语即使有正的句时长，若连续重复段落中大多数字词时间已经坍缩，也须恢复或明确失败；正常副歌保留，不能只凭重复次数删词。
没有独立音频分类证据的未覆盖段落仍按原门槛拒绝。ASR 时间只作粗定位，不代表人工起音准确率。

在目标硬件上先比较 batch 1 与候选大小的文字和时间，再完成实际歌曲的七项产物验收。
识别 batch 与分离 batch 独立，不能把预下载、识别完成或吞吐对照计为整首音频通过。
音频控制器保留历史失败；同源预下载在登录失败之后完成，或改用新的本地识别版本解决远程推理阻塞时，
允许新的音频尝试。来源站点的退避仍保留，本地识别不受远程模型配额的退避影响。

| `KARAOKE_PORT` | 默认 `8746` |
| `KARAOKE_HOST` | 默认 `127.0.0.1`；需要局域网设备点歌时可显式设为 `0.0.0.0` |
| `KARAOKE_CORS_ORIGINS` | 允许调用接口的前端来源，逗号分隔；默认允许本地 8745 预览页 |
| `KARAOKE_DEVICE` | 默认 `auto`：CUDA → MPS → CPU；也可显式指定 |
| `KARAOKE_SEPARATOR_PYTHON` | 分离环境的 Python；本机默认复用已有 `audio/.venv-separator-local` |
| `KARAOKE_SEPARATION_BATCH_SIZE` | 分离窗口批量大小，默认 `1`；按显存实测选择 |

| `KARAOKE_MAX_DURATION_SECONDS` | 默认 `900` |
| `KARAOKE_COOKIES_FILE` | 可选的 yt-dlp cookies 文件路径；未指定时读取数据目录的 `private/youtube-cookies.txt`。每次下载检查文件，存在则使用，缺失则默认下载；登录失败不会自动退回匿名重试。导出浏览器 cookies 需用户授权，服务本身不读取浏览器；私有目录权限 0700、文件 0600，不提交或上传 |

单进程、单 GPU 队列运行；不要给同一数据目录启动多个 Uvicorn worker。`none` 模式下所有已点歌曲可进入流水线，同一种重阶段仍串行，不同阶段可以交错；`/health.preparation_concurrency` 返回 `null`，`running_jobs` 和房间快照的 `preparation_jobs` 列出全部在途任务，旧单数属性保留首项。暂停领取任务后，所有已经开始的歌曲仍会自然完成。并发处理各自监控共享缓存，并按运行任务数预留写入余量。独立的分离环境与主环境都需安装对应硬件的 PyTorch。CUDA 入口已接入；本次实际端到端运行平台是 Mac / MPS，未在 RTX 4090 上测时。

维护时可在数据目录创建 `preparation.pause`，暂停领取下一项预处理任务；当前任务正常完成，歌单、排队顺序和缓存保护保持不变。该暂停跨服务重启保留，删除文件后继续，`/health.preparation_paused` 显示状态。批量回归应先暂停控制器，再暂停预处理；定向复现失败样本后才恢复整批。

服务重启后恢复排队任务；被中断的运行任务标为失败，保留日志和中间文件，不假装完成。失败任务可以重新提交；已完成且文件完整的相同请求直接命中缓存。

## 音乐与视频搜索

`GET /v1/search?q=歌名或歌手&provider=youtube`。只支持 YouTube；B站搜索返回 422。返回平台第一页的全部可用单视频链接，字段为 `url`、`title`、`uploader`、`thumbnail`、`duration`（秒）、`views`、`provider`。查询限 1–160 字。搜索不创建任务，也不读写歌曲缓存。

前后端保留 YouTube 的结果顺序和数量，没有 3 条截断，不按字面关键词、认证、直播状态额外过滤。仅校验单视频 URL 和封面地址。前端在「YouTube 视频」标签展示，本地曲库在独立标签查看。服务端相同查询合并请求，元数据缓存 120 秒、最多 32 项；最多并行 2 个查询、待处理最多 8 个，每次含等待最多 25 秒。超量返回 429，平台错误返回 502，成功无结果返回空数组。复用 yt-dlp 解析一个完整原生搜索页，不无限抓取后续页面，无需额外 API key。

`GET /v1/music/search?q=关键词&kind=songs|artists` 用 ytmusicapi 读取 YouTube Music 完整第一页，默认 songs。歌曲包含标准 YouTube `url`、`title`、`artists`（名称与可用的频道 ID）、`album`、`version`、`duration`、平台提供的 `views`、`available`、`thumbnail` 和原始 `rank`。歌手返回 `title`、`browse_id`、频道 `url`、`thumbnail`、`rank`；`provider=youtube_music`。不自动选择同名歌手或删改版本。

`GET /v1/music/artists/{browse_id}` 只接受 YouTube 频道 ID，读取歌手页及其完整热门歌单，返回歌手元数据、`results`、`order=youtube_music_top_songs`、`complete`。没有歌单链接时保留页面精选并标 `complete=false`。平台未提供播放量时保留空值。前端默认平台顺序；播放量排序仅作用于当前返回的、计数可知的结果，未知计数排后。这两组接口复用视频搜索的限流、超时、缓存与去重，不下载音视频或创建准备任务。

从结果点歌使用 `POST /v1/room/entries`，例如 `{"url":"视频链接","source_title":"搜索返回的视频标题"}`。`source_title` 只给新任务提供临时展示标题（最多 500 字），不参与缓存键，不覆盖后续元数据；用户显式传入的 `title` 仍是优先标题。处理中的 `song_info` 按字段合并，空对象、空字符串或 `null` 不清除已知信息；下载进度、语言识别等更新不能把已有歌名变回占位文字。已有准备任务优先用 `job_id` 加入。
