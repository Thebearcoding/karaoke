# 主唱／伴唱分离的性能调查（2026-10-05）

目标是减少点歌到能唱的等待时间，同时保留背景音乐、伴唱和主唱。通用的“人声／伴奏”分离不能替代主唱／伴唱分离。以下区分本项目实测、外部报告和待验证方案。

## 2026-10-05 的瓶颈记录

本机为 Apple M4 Max、128 GiB 内存，使用 PyTorch MPS。Unravel（238.36 秒）本次完整准备耗时 139.51 秒，其中全部人声分离 49.08 秒、主唱分离 75.74 秒。阶段计时包含各自子进程的导入、模型加载、推理和文件输出；这不是只测模型 forward，也不是系统清缓存后的严格冷启动。

主唱使用 Anvuew BS-RoFormer，输入为前一步已经分出的全部人声。字幕对齐和画面渲染与主唱分离并行：画面在第 118.36 秒完成，主唱在第 129.48 秒完成，随后封装。因此单独减少主唱阶段前约 11 秒会直接减少此次等待；继续提速后，字幕／画面分支会成为瓶颈。不能把并行阶段的秒数相加推算总耗时。

## 可选路线

| 路线 | 证据 | 判断 |
| --- | --- | --- |
| 现有模型运行在 H200 | 本项目 2026-10-02 的另一首 181.44 秒样本：Mac 主唱阶段 63.50 秒，H200 batch 1 为 12.40 秒（其中推理 7.74 秒） | 已有直接证据；约 5.1 倍阶段提速。尚不含新增传输、远端排队和整条流水线，不能套成 Unravel 的端到端时间 |
| Apple MLX 后端，保留训练权重 | [项目发布验证](https://github.com/ssmall256/mlx-audio-separator/blob/main/docs/release-validation.md)报告 M4 mini 上另一款 BS-RoFormer 的 12 首 ABBA 对照为 2.16 倍 | 最值得本机试验。Anvuew 本身的兼容性、波形差异和端到端收益尚未实测 |
| 增大 batch | 上述 H200 主唱推理 batch 1/2/4 分别 7.74/7.41/7.29 秒，整个阶段 12.40/12.15/12.01 秒 | batch 4 只减少约 3% 阶段耗时，优先级低。批量输出数值差异仍需评估 |
| 换轻量主唱模型 | [MVSEP 官方比较](https://mvsep.com/algorithms/76?lang=en)中 Anvuew 主唱 SDR 10.22；较老的 Karaoke 模型约 6.42–8.28 | 没有同效果、更快的证据。不能为了速度直接降低伴唱保留和主唱抑制质量 |
| 直接从原始混音提取主唱，与全部人声模型并行 | MVSEP 支持直接提取主唱，也支持先分离全部人声；这是不同输入分布 | 值得独立实验，但不是等价重排。需检查减法得到的伴唱是否引入伴奏和伪影，以及两模型争抢 GPU 后的耗时 |

SDR 是有参考分轨时的失真指标；不同测试集和输入路线之间不能直接比较。本项目没有针对 Unravel 的独立原始分轨，不能把模型之间的波形相似度写成分离准确率。

## 本机试验应怎样做

优先比较同一 Anvuew 权重的 MPS 和 MLX，固定输入哈希、44.1 kHz 双声道、增益、640000 样本窗口、50% 重叠、边界 padding、FP32 和累加方式。分别记录模型转换／首次加载、进程启动到产物、预热后推理和整首等待时间。只替换推理内核，先不改变窗口或精度。

MLX [实现](https://github.com/ssmall256/mlx-audio-separator/blob/2f55dca7441cf8b243f4937d28dfe3dc4d60a8d3/mlx_audio_separator/separator/models/roformer/loader.py)有 BS-RoFormer 的配置和权重加载路径；[调优文档](https://github.com/ssmall256/mlx-audio-separator/blob/main/docs/tuning.md)默认 FP32、编译 transformer、延后清缓存。文档也明确指出该 RoFormer 路径的 bf16 没有测出加速，因此不能假定半精度必然更快。库默认的切片、padding 和 overlap-add 必须与当前 runner 逐项核对，不能只换一次 CLI 调用便声称等价。

至少用独唱、密集和声、重伴奏、短片段和长音留出样本检查：主唱残留、伴唱误删、伴奏损伤、伪影、窗口接缝、有限数值、帧数和完整解码。结果可接受后才更换正式后端，并在同一实际版本下重新验证。当前正式路径继续使用原模型和 batch 1；本调查没有把未实测的 MLX 速度或质量记为通过。

## 同一输入的 Mac / H200 计算对照

2026-10-05 PT，用 Unravel 的 238.36 秒缓存音频和同一份 52 行网络歌词，分别重新执行全部计算。下载、metadata 和歌词检索留在本机；本次固定它们的输出，计时不含这些网络阶段，也不生成视频。两个有效运行均使用 `dc9c6fa`、相同模型权重和配置、batch 1，无阶段计算缓存复用。模型文件已下载并读取校验，系统文件缓存已热；每个阶段是新进程、新加载的模型，不是常驻模型的热推理。

- 本机：Apple M4 Max，128 GiB，MPS。
- 远端：单张 NVIDIA H200，CUDA；主机 Intel Xeon Platinum 8480C。没有使用其余七张 GPU。
- 算法代码、分离器实现和 56 个模型／配置／对齐器文件哈希一致。分离环境 PyTorch 为 Mac 2.13.0、H200 2.11.0+cu130；对齐环境均为 2.11.0，Numba 分别为 0.63.1 / 0.67.0。因此这是两个实际运行环境的单次对照，不是隔离软件版本变量的硬件微基准。

### 阶段耗时

单位为秒；阶段包含各自的导入、加载、计算和输出。**并行阶段不能相加当成总等待时间。**

| 阶段 | Mac | H200 |
| --- | ---: | ---: |
| 完整计算 | 128.529 | 76.196 |
| 音频解码 | 0.604 | 1.081 |
| 原采样率解码 | 2.162 | 2.204 |
| 读取准备好的歌词 | 0.002 | 0.002 |
| 全部人声／伴奏分离 | 48.466 | 14.989 |
| 人声重采样 | 0.128 | 0.866 |
| 主唱／伴唱分离 | 72.231 | 15.117 |
| 双轨整理 | 2.454 | 3.151 |
| Whisper 逐词对齐 | 21.273 | 18.240 |
| SOFA 音素精修 | 9.096 | 12.251 |
| 重复唱段修复 | 6.543 | 13.273 |
| 上下文对齐 | 11.230 | 12.862 |
| 三轨导出 | 6.181 | 14.668 |

完整计算减少 52.333 秒（40.7%），速度为本机的 1.69 倍。包含进程启动和控制器轮询的观测墙钟为 129.846 / 78.940 秒；后续独立产物校验不在这两个计时内。

本机关键路径为分离：主唱在 121.559 秒完成，三轨在 128.101 秒导出。H200 三轨在 46.884 秒就已完成，但歌词分支到 76.184 秒才结束。继续只加快主唱模型不会同比缩短 H200 总等待。

### 推理与启动开销

分离器内部计算：全部人声 43.865 → 8.161 秒，主唱 69.651 → 10.092 秒。Whisper 对齐计算 15.892 → 5.187 秒，但模型加载 3.572 → 10.665 秒。SOFA 音素内部计算 2.887 → 2.190 秒，上下文内部计算 6.444 → 2.683 秒；它们的整个阶段却没有提速，说明需要处理模型重复加载、导入和其他 CPU 工作。重复段的内部计时为 4.210 → 9.397 秒，包含音频特征、DTW、按需加载模型和参考段对齐，不能当作纯 GPU forward。

下一步优先验证 H200 常驻模型、在音素和上下文阶段复用 SOFA 实例。CPU 密集的音频整理与重复段处理是否留在本机，需要连同中间文件传输一起测量，不能仅凭设备名称决定。

### 输出一致性与计时边界

两边都生成并校验了三条 float64 WAV、三条完整 MP3 和字幕；回传后再次核对七项文件哈希。两边均为 52 行、396 个高亮单元、100 个回退单元、零未定位行。文本完全相同，但 18 个单元的起点有差异，其中 7 个超过 50 ms、4 个超过 100 ms，最大 427 ms。词级中间结果已有 8 个差异，后续音素／上下文处理进一步改变局部结果。没有独立人工标注，不能判断哪边更准确，也不能宣称效果等价。

全曲波形差异：伴奏 RMS 为 8.37e-7，主唱和伴唱约 2.08e-4，后两者峰值差约 0.020；这些是跨环境数值差异，不是分离质量评分。正式后端未因此更换。

独立传输测量使用 brix/rsync，包含命令和连接建立：5.77 MB 输入包上传 4.96 秒，13.42 MB 的 MP3＋字幕回传 8.30 秒，562.60 MB 的全套无损产物与诊断回传 46.24 秒。它们不计入上述计算时间，三次独立测量之和也不是完整线上 E2E 实测。保留远端无损母版、只回传播放文件更值得作为候选验证。

原始证据保存在运行目录 `service-data/compute-profile-20261005/`：`mac/profile.json`、`h200/profile.json`、`comparison.json`、各阶段时间线、输入／权重哈希、传输记录和输出文件。首次 H200 启动曾因工作目录覆盖 `PYTHONPATH` 而执行旧代码，在歌词实现指纹检查处失败；其诊断保存在 `h200-wrong-code-attempt/`，未计入性能结果。修正启动路径并验证实际模块文件后，才得到上面的有效完整运行。

## 2026-10-07：实际等待时间与渲染优化

上面的 128.529 / 76.196 秒是旧版本、单首固定输入的**音轨与字幕计算**，不包含下载、找歌词、生成 MV 或远端传输；不能据此承诺本机两分钟、远端一分钟就能唱。当前网页仍在 Mac 上计算，之前的 H200 对照没有替换正式后端。

近期真实任务的完整处理时间为：First Love 197.897 秒、童話 202.026 秒、後來 276.820 秒、老男孩 252.563 秒。这些是任务开始处理至产物完成，不包含等待工位，也不是多首重复测量的统计分位数。当前版本还包含后续新增的局部起音校验，不能直接与旧流程比较。

本次保持模型、切片、精度、画质、字幕时间和校验不变，只优化字幕描边：在有文字的区域及完整滤镜边界内计算，不再对透明画布的空白区域做最大值滤波。透明边缘、抗锯齿和画布边界均与原实现逐像素比较。

### 同一真实输入上的分项对照

M4 Max、128 GiB、持续接电；同一份 238.36 秒原始视频和 49 行字幕，编码参数一致。每种方案重复两次，后半程反向顺序运行。均值如下：

| 方案 | 渲染耗时（秒） | 处理结果 |
| --- | ---: | --- |
| 原实现 | 10.504 | 对照 |
| 仅缩小描边计算区域 | 7.574 | 最终采用，减少 2.929 秒（27.9%） |
| 缩小描边区域，并将滤镜线程设为 1 | 11.669 | 比原实现更慢，撤回线程改动 |

六次视频解码后的 SHA-256 完全一致。描边最大值滤波的单次分析耗时约 3.625 → 0.563 秒；线程数下降则增加了向 FFmpeg 写入帧时的等待。该结果说明应减少多余计算，而不能假定减少线程就能降低延迟。

### 不把阶段提速当作整首提速

包含线程限制的初始候选，完整计算与 MV 生成实测 171.739 → 171.733 秒，几乎没有变化。该对照固定缓存音频及可信歌词、重做全部计算、每阶段新进程和模型加载；系统文件缓存已热，计时不含网络、排队及浏览器加载。两边三条 MP3、字幕和 MV 的文件哈希相同；WAV 文件哈希不同，各自通过完整解码、有限值、原采样率和帧数检查，不声称无损文件位一致。此候选没有部署。

另一个固定字幕的实验以已有 MV 和 31 行字幕为输入，初始候选渲染均值 19.768 → 18.313 秒；不能用这个输入上的收益推断原始视频或全流程的收益。最终方案去掉了线程限制，仅保留描边优化。几秒的渲染节省不能被写成已经解决三至四分钟的整体等待；主要耗时仍在两个分离模型以及局部起音复核。

这仍是少量样本，不是跨歌曲延迟保证。前期实验曾在电池低电量模式和接电之间切换，均保留作诊断但排除在加速结论之外；没有修改系统电源设置。证据位于运行目录 `service-data/e2e-20261007/`，包括 `render-factors-render-report.json`、各次完整流程报告、每五秒的 `power.jsonl`、原始阶段日志和测试结果。

## 2026-10-08：减少重复计算，保留原有结果

本轮保持模型、FP32 推理、50% 窗口重叠、字幕时间、720p/30 fps 和 CRF 19 不变：

- 单目标分离沿用原有窗口与叠加顺序。末尾重复窗口复用同一次预测，仍执行每一次原有叠加；也不再为同一单目标复制多份全曲累加缓冲。较大 batch 和多目标路径保持原行为。
- 三条播放音轨同时编码，避免第三条等待前两条。完整解码、共同增益及削波时全组重编码保持原样。
- 每句先合成一次琥珀色字形，每帧只在字形范围内按原二值扫亮遮罩取像素。下一句预读底图也只在内容改变时合成。时间、排版、透明边缘和逐词进度不变。
- 片头和背景遮罩 PNG 只解码一帧，由 overlay 的帧同步复用，不再循环读取和解码静态图片。实际编码测试检查图片输入结束后的片头与遮罩仍然可见。

对照通过普通点歌 API 和 worker 执行，以提交请求至 SSE 通知可唱为边界。两边固定同一原始视频和歌词正文缓存，重新执行分离、对齐与完整 MV 渲染；不把下载速度、旧阶段缓存或音轨就绪冒充整首提速。逐曲保留耗时和重叠时间线，并比较三轨样本、播放文件、完整字幕及 MV 解码结果。

这轮同样撤回了 `filter_complex_threads=1`：40 秒动态片段的六对测量没有稳定收益，完整 Unravel 的两对热进程测量为默认 12.32 秒、限制线程 23.39 秒。输入是否包含片头、静态背景遮罩与完整字幕，足以改变瓶颈；不能用简化片段选择全局编码参数。两个条件的成片字节均相同。

原始证据保存在运行目录 `service-data/e2e-separation-render-20261008/`。First Love 的首次基线在字幕时间校验处失败，保留为独立诊断，不计作完成时间或性能收益；正式前后对照使用 Unravel。
